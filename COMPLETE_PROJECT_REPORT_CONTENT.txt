1. INTRODUCTION

1.1 Overview of Women Safety Problem
Women face safety risks in public spaces, during travel, and in isolated environments. Delays in communication during emergencies often increase the severity of incidents. A technology-based response system can reduce this delay and improve rescue outcomes.

1.2 Need for a Smart Safety Application
Traditional safety methods depend on manual calls or nearby help, which may not be available in critical situations. A smart app can detect distress, share location instantly, and alert trusted contacts using multiple channels. This creates faster and more reliable emergency response.

1.3 Problem Statement
Existing safety applications usually focus on one feature, such as SOS or tracking, but lack complete integration. Many solutions fail when one communication channel is unavailable. The project aims to build a unified women safety platform combining SOS, live tracking, backend alerts, and intelligent risk support.

1.4 Objectives of the Project
The objective is to design and develop a mobile-based women safety system with real-time SOS activation, guardian notifications, live location sharing, and emergency evidence capture. Another objective is to provide a secure backend API for authentication, alert management, and role-based access. The project also targets improved reliability through multi-channel communication and scalable architecture.

1.5 Scope and Limitations
The system covers personal safety workflows for registered users, emergency contacts, and administrators. It includes Android-focused mobile implementation, backend APIs, and cloud messaging support. Limitations include dependency on internet/GPS availability and third-party platform configurations.

================================================================================

2. LITERATURE REVIEW

2.1 Existing Women Safety Solutions
Current solutions include standalone SOS apps, wearable panic devices, and location-sharing applications. Some systems are effective for basic alerts but offer limited integration with backend analytics or intelligent detection.

2.2 Review of Mobile Emergency Systems
Mobile emergency systems generally provide panic buttons, GPS tracking, and emergency messaging. Advanced systems include sensor-based triggers and push notifications. However, many lack continuous monitoring and coordinated response orchestration.

2.3 Limitations in Existing Systems
Common gaps are single-channel dependency, poor escalation logic, and weak verification of alert delivery. Some apps also suffer from limited usability under stress and inconsistent real-time performance.

2.4 Proposed Women Safety App Approach
The proposed system integrates mobile app and backend services for a complete emergency pipeline. It supports multi-channel notifications (SMS, WhatsApp, email, push), live tracking, and centralized alert handling. This approach improves reliability, speed, and operational visibility.

================================================================================

3. SYSTEM ANALYSIS

3.1 Requirement Analysis
The project requires a responsive mobile interface, secure authentication, GPS/location tracking, real-time notification delivery, and backend persistence for emergency records.

3.1.1 Hardware Requirements
A modern Android smartphone with GPS, camera, microphone, and internet connectivity is required for full feature use. Development requires standard laptop/desktop hardware.

3.1.2 Software Requirements
Flutter SDK, Dart, Android Studio/VS Code, Firebase setup, and Google Maps configuration are required for app development. Backend requires Java 17, Spring Boot, Maven, and PostgreSQL.

3.2 Feasibility Study
The project is evaluated on technical, economic, and operational feasibility to ensure practical deployment and long-term maintainability.

3.2.1 Technical Feasibility
The selected stack (Flutter + Spring Boot + Firebase + PostgreSQL) is mature and widely supported. APIs, cloud services, and notification tools are available for implementation.

3.2.2 Economic Feasibility
Development tools are mostly open-source, reducing initial cost. Cloud usage can be scaled gradually, making the solution cost-effective for pilot and production phases.

3.2.3 Operational Feasibility
The system is designed for simple emergency activation and quick guardian interaction. Its workflow is practical for daily use and does not require complex training.

3.3 Functional and Non-Functional Requirements
Functional requirements include registration/login, SOS trigger, location sharing, and alert management. Non-functional requirements include security, reliability, low response latency, availability, and usability under stressful conditions.

4. SYSTEM DESIGN

4.1 Overall Architecture (Flutter + Spring Boot)
The frontend is a Flutter mobile app, and backend services run on Spring Boot REST APIs. PostgreSQL stores operational data, while Firebase Cloud Messaging handles push notifications. This layered architecture separates presentation, business logic, and data access.

4.2 Data Flow Design
User actions initiate API requests through authenticated tokens. Emergency events are sent to backend, validated, persisted, and forwarded to communication channels. Guardians and admins receive alerts and status updates in near real-time.

4.3 Database Design (Users, SOS Alerts, Location Logs, Danger Zones)
Core tables include users, emergency contacts, sos_alerts, location_logs, and danger_zones. Relationships ensure user-centric tracking and historical alert analysis. The schema supports reporting and future intelligence modules.

4.4 UML Diagrams (Use Case, Class, Sequence)
Use Case diagrams show interactions among user, guardian, and admin roles. Class diagrams define entities and service relationships. Sequence diagrams model end-to-end emergency flow from trigger to resolution.

4.5 API Design and Security (JWT, Role-based Access)
REST endpoints are grouped for authentication, SOS operations, and admin actions. JWT tokens secure requests, and role-based access prevents unauthorized operations. Passwords and sensitive data follow secure handling practices.

5. SYSTEM DEVELOPMENT

5.1 Development Methodology
An incremental and modular development approach was followed. Features were implemented in phases, tested continuously, and refined based on integration results.

5.2 Tools and Technologies Used
The project uses Flutter for cross-platform UI, Spring Boot for backend APIs, and PostgreSQL for data management. Firebase services support push notifications and real-time communication needs.

5.2.1 Flutter, Dart, Firebase, Google Maps
Flutter and Dart provide a fast UI development workflow with reusable components. Firebase enables notification and cloud integration. Google Maps supports live location visualization and route-based safety features.

5.2.2 Spring Boot, Java 17, PostgreSQL, FCM
Spring Boot and Java 17 provide robust backend service development. PostgreSQL stores transactional and tracking data. FCM enables scalable delivery of push alerts to mobile devices.

5.3 Core Modules Developed
The implementation is divided into core modules to ensure maintainability, clarity, and independent testing.

5.3.1 Authentication and User Management
This module handles registration, login, token generation, and profile data. It ensures controlled access to emergency and dashboard features.

5.3.2 SOS Trigger and Alert Escalation
This module activates emergency workflows instantly and marks alerts with status transitions. Escalation logic ensures repeated and multi-target notification when acknowledgments are delayed.

5.3.3 Live Location Tracking and Route Monitoring
The module captures and updates user location during emergencies or monitored journeys. It supports continuous sharing with guardians and route deviation detection.

5.3.4 Multi-channel Notification (SMS, WhatsApp, Email, Push)
Alert messages are dispatched across multiple channels to reduce delivery failure risk. This increases reliability compared to single-channel systems.

5.3.5 AI/ML Risk Features and Distress Detection
AI-assisted components support risk indication and distress pattern analysis. These features enhance preventive safety by identifying potential danger trends.

6. SYSTEM IMPLEMENTATION

6.1 Flutter Mobile Application Implementation
The mobile app was implemented using structured screens, reusable widgets, and service-driven architecture. Emergency workflows are optimized for minimal user interaction time.

6.2 Backend API Implementation
Backend APIs were built with controller-service-repository layers for separation of concerns. Endpoints support authentication, alert creation, status updates, and administrative operations.

6.3 Firebase and Notification Integration
Firebase configuration enables push messaging and notification tokens. The system maps users to device tokens and triggers real-time alerts during emergency events.

6.4 User Interface and User Experience Design
The UI prioritizes clear action buttons, high visibility, and quick navigation in stress scenarios. Important emergency controls are always accessible and visually prominent.

6.5 Deployment and Configuration Setup
Backend deployment is supported through Docker/local setup with environment configuration. Mobile app setup includes API base URL, Firebase files, and required permissions.

7.1 Testing Strategy (Unit, Integration, System Testing)
Unit tests verify individual components, integration tests validate communication between modules, and system testing checks complete emergency workflows.

Test scenarios include login flows, SOS activation, location updates, notification delivery, and admin resolution actions. Negative tests cover invalid inputs and failure handling.

7.3 Device and Real-time Feature Testing
Testing on physical devices validates GPS behavior, push notifications, and UI responsiveness under real conditions. Real-time checks confirm acceptable latency and event sequencing.

7.4 Result Analysis and Screenshots
Results indicate successful execution of core safety workflows with stable backend response. Screenshots and logs demonstrate feature completion and operational consistency.
